# Idempotency keys on every write API

This decision makes idempotency a platform rule rather than something each team designs on its
own. It came directly out of the duplicate charges caused by the old synchronous checkout in
[ADR-003](adr-003-sync-capture.md), and it is relied on by the checkout saga in RFC-010, the
payout ledger in RFC-013 and every public write endpoint. The shared client libraries
implement the client side so that teams do not have to.

## Context {#context}

Networks fail in ambiguous ways. When a client sends a request and the connection drops before
the response arrives, the client cannot know whether the server acted. Mobile clients on poor
connections, automatic retries in our HTTP libraries, and impatient buyers pressing a button twice
all produce repeated requests. For reads this is harmless. For writes it creates duplicate orders,
duplicate listings and, worst of all, duplicate charges: under the old checkout about 30 buyers per
100,000 orders were charged twice.

Each team had started inventing its own de-duplication, with different header names, storage
durations and behaviours when a duplicate arrived. Some returned an error, which made clients
show a failure for an operation that had in fact succeeded. We needed one consistent mechanism.

## Decision {#decision}

Every API endpoint that creates or changes state requires an `Idempotency-Key` header. The client
generates the key, a random UUID version 4, once per logical operation, for example when the
checkout page loads, and reuses it for every retry of that operation. Requests without a key are
rejected with 400.

The server stores the key, the authenticated account, a hash of the request body and the response
status and body, in the service's own database, for 24 hours. When a request arrives with a key
already stored for the same account:

- if the body hash matches and the original request has finished, the stored response is replayed
  byte for byte, with a header marking it as a replay;
- if the original request is still in progress, the server answers 409 and the client retries
  after a short delay;
- if the body hash differs, the server answers 422, because the client has reused a key for a
  different operation.

Services that call external providers, such as the payment processor, pass a key derived from the
client's key, so the provider de-duplicates too.

## Consequences {#consequences}

Retries are now safe everywhere, and clients can retry automatically without asking the user. In
checkout this removed duplicate charges: a retried "Place order" returns the original order
instead of charging again, and the processor ignores repeated authorise and capture calls carrying
the same key. Support no longer issues refunds for duplicates.

The costs: every write path pays one extra indexed lookup and insert, adding about 2 milliseconds
at p50. Key storage is roughly 40 GB across services at current volume, cleaned up hourly. Clients
must manage keys correctly; a client that generates a new key on every retry gets no protection,
so the shared client libraries generate and persist keys for each operation. A retry arriving more
than 24 hours later is treated as a new request, which is acceptable because no client retries
that late.

## Alternatives considered {#alternatives}

- Server-side de-duplication by comparing request bodies within a time window. Rejected because
  two genuinely separate identical purchases would be merged.
- Natural keys per domain, such as basket id for checkout. Works for some operations but not for
  all, and gives no consistent behaviour across APIs.
- Keeping keys for 7 days. Rejected as costly with no practical benefit over 24 hours.
